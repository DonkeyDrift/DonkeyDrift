# WebRTC 90 kHz 时间戳修复设计

日期：2026-10-31

状态：规范已获批准，代码与自动验证完成；浏览器性能验收待车端加载新代码。

## 目标与边界

修复 `DriveAiortcVideoTrack` 因 `1/fps` 时基和整帧单调保护导致的媒体时钟超前。
仅修改轨道时间戳及直接相关注释、测试，不更换编码器，不修改 Unity、
浏览器接收策略、车辆控制链路或 `myconfig.py`。

保留 `fps` 对补帧周期的控制，保留补帧默认值和环境变量开关。
本轮浏览器对比使用 `DRIVE_WEBRTC_FRAME_PACING=0` 和
`DRIVE_WEBRTC_FRAME_STAMP=1`，不以重复帧冒充真实 60 FPS。

最终性能目标是浏览器真实呈现延迟 p95 小于 20 ms、帧率接近 60 FPS。
本修复首先验收时间戳正确性；若浏览器仍未达标，记录未达标，不扩大修改范围
或宣称时间戳修复已解决全部延迟。

## 已有证据

- 当前实现：`time_base = Fraction(1, fps)`，采集时间差乘 `fps` 后取整；
  当目标 PTS 不大于上一 PTS 时，增加一整帧。
- 通过实际轨道 `_emit` 输入 6000 帧，时间序列为
  `i / 60.1 + (0.004 if i % 2 else 0)`，关闭补帧。
  最后一帧源时间为 99.820972 s，媒体时间为 99.983333 s，
  超前 162.362 ms，`pts_bumps=5627`。
- 这证明时间戳逻辑存在漂移缺陷，但不是全部浏览器延迟的因果证明。
- 此前关闭补帧的同会话短采样，浏览器约 58–60 FPS，呈现延迟 p95
  约 41–43 ms；这些短窗口不是长期验收结论。

## 时间戳规则

### 时基和新帧

1. 轨道使用固定 `time_base = Fraction(1, 90000)`，与 RTP 视频时钟一致。
2. 首帧 PTS 为 0，保存首帧采集时间作为时间轴锚点。
3. 真实新帧的目标 PTS 为采集时间相对锚点的秒数乘 90000 后四舍五入。
4. 实际 PTS 为目标值与上一 PTS 加 1 的较大者，保证严格递增。
   单调保护的最小增量为一个 tick，约 11.1 微秒，不是 16.7 ms。
5. `fps` 不参与时间戳换算。30 FPS、60 FPS 以及不均匀输入均使用同一时基。
6. 时间戳回拨或相同时间戳时保持单调，不在本轮引入墙钟校正系统。
   回拨期间不承诺与原始采集时间完全对齐。

### 重复帧

重复帧的像素印章仍使用原始采集时间，使浏览器能按内容首现去重。
媒体 PTS 则随真实经过的时间推进，不能复用旧采集时间后反复只加一个 tick。

每次发出真实新帧时，记录该帧实际媒体 PTS 与对应单调钟时刻。
后续重复帧的目标 PTS 为这个媒体 PTS 加单调钟经过时间乘 90000。
重复帧与真实新帧共用严格递增保护；新帧若紧随重复帧到达，
允许被保护到上一 PTS 加一个 tick，不顺延一整帧。

既有补帧预算、等待策略、源静默停止机制保持不变。本设计不保证补帧开启时
所有新帧的媒体 PTS 都能完全保留采集间隔；开启状态单独做兼容性回归。

### 指标

保留 `pts_bumps` 字段，仅在真实新帧目标 PTS 不大于上一 PTS 时增加。
同步修正直接相关注释：该数值不再代表增加一整帧的延迟，
也不能换算为 `pts_bumps * 16.7 ms`。

保留原有 `stale_frames` 语义：等待新帧的计数，不是丢帧数。
不增加新接口、新配置或性能字段。

## 测试方案

主要测试文件：`tests/test_drive_webrtc_track.py`。
同时运行 `donkeycar/tests/test_drive_api_bridge.py` 和相关编码器测试。

更新旧时基断言，优先断言 `pts * time_base` 的秒数，不将帧号当作 PTS。
必须覆盖：

1. 首帧为 0；1 s 与 2.5 s 对应 90000 与 225000 ticks。
2. 30 FPS 与 60 FPS 均为 90 kHz 时基。
3. 交替长短间隔的新帧保留实际时间间隔，不挤到整帧格点。
4. 上述 6000 帧轻微超频复现序列，关闭补帧时相对采集时间误差
   不超过一个 tick，且没有逐帧累计超前。
5. 同时间戳及回拨严格递增，单次保护只增加一个 tick。
6. 重复帧 PTS 随单调钟推进；原采集印章不变。
7. 重复帧后立即到达新帧，媒体 PTS 不因保护增加一整帧。
8. 既有补帧出帧计数、等待、源静默停止、环境变量开关测试通过。
9. 真实 PyAV/VP8 编码接受新的时间基，生成 RTP 时间戳严格递增。

时间戳序列测试应使用可控时钟，不以线程调度或真实等待决定数值断言。
与时间相关的既有补帧测试需调整为秒数断言，同时保留原来的出帧行为断言。

## 浏览器验证

在同一浏览器、分辨率、刷新率及模拟器配置下对比修改前后：

- 重连新会话后预热 30 秒，再连续采样至少 120 秒，每 2 秒读取一次统计。
- 确认 `active=true`、会话未切换、`e2e_samples>0`、真实源帧率约 60 FPS。
- 报告真实源帧率、发送帧率、浏览器帧率、呈现间隔 p95、
  延迟 p50/p95 和 `pts_bumps` 增量的范围，不仅挑选最好窗口。
- 性能目标：至少 95% 的有效稳态窗口同时满足浏览器帧率不低于 59 FPS、
  呈现延迟 p95 小于 20 ms；窗口 p95 不是全部原始帧合并后的总体 p95。
- `jitter_buffer_delay_ms` 当前是会话累计均值，不能当作每个窗口实时值。
- 时间戳印章的起点是模拟器帧到达车端，不含此前 Unity 渲染；
  `e2e_display` 基于浏览器预计显示时间，不是物理屏幕测量。

重启车端会中断驾驶和视频连接，执行前先停车并确认重启时机。
不自动强杀现有 TUI、后端或模拟器。不额外启动探针接管浏览器会话。

## 实施与验证结果

- `drive_api_bridge.py` 已改为 90 kHz 时基；真实新帧按采集时间推进，
  重复帧按最近真实新帧的媒体时间和单调钟经过时间推进。
- 单调保护最小增量为一个 tick；同步修正轨道、测试及 API 类型中的相关注释。
- 轨道、桥接、VP8 编码及上游编码器契约测试共 90 项通过。
- 原 6000 帧复现序列：最大绝对误差 0.005546 ms，
  最终媒体时间偏差 -0.005047 ms，`pts_bumps=0`。
- 独立本机 WebRTC 双 peer 回环成功接收并解码 10 帧，
  接收时基为 `1/90000`，PTS 严格递增，源 `pts_bumps=0`。
  此验证未连接现有后端、未接管浏览器视频会话。
- `git diff --check` 通过。
- 现有浏览器仍由已启动的车端进程供帧，未执行重启或强杀。
  现有会话数据不能作为新实现的性能结果；尚不能宣称达到 20 ms 或稳定 60 FPS。
