# WebRTC 第一阶段：降低观测开销

## 目标与基线

仅优化浏览器指标采集，不改变编码、控制、模拟器 FPS 或接收缓冲策略。
2026-11-01 两次运行采样：源、发送、接收约 60fps，浏览器回调统计
41～45fps，实际编码 2.8～3.4ms，预计显示 E2E 中位数 46～49ms，
P95 为 51～53ms。该基线不是屏幕出光实测，也未证明像素读回是瓶颈。

## 方案比较

1. 关闭印章：观测开销最低，适合作为 FPS 对照，但失去跨链路像素时间戳测量。
2. 日常低频采样，诊断逐帧采样：推荐。保留 E2E 观测，减少日常同步像素读回。
3. 始终逐帧采样：保留现有首现去重能力，但不解决观测开销问题。

## 行为设计

- FPS 及帧间隔继续在每次 requestVideoFrameCallback 更新。
- 日常模式：印章探测及激活后的读回均按单调时钟限频至最多 15Hz，
  不用每 N 帧计数代替时间限频；首个具备测量条件的回调立即尝试采样。
- 诊断模式：沿用现有逐帧像素读取与印章去重逻辑。
- 沿用现有诊断模式入口，不增加后端接口或车端配置。关闭车端印章的
  FPS 对照属于独立实验，不强行将缺失印章的 captureTime 估计标成精确值。
- 日常低频样本表示被抽中内容的本次呈现年龄，不能保证捕获该内容首次呈现。
  重复帧按印章去重，但去重不能消除漏过首现带来的偏差。
- UI 提示及注释明确区分抽样 E2E 与逐帧诊断；不得宣称两种统计完全等价。
- 保留现有回调时刻、presentationTime、expectedDisplayTime 三种锚点，
  不混用预计显示时延和回调时延；预计显示时间不等于屏幕出光时间。
- E2E 继续保留最近 240 个有效样本，日常 15Hz 下覆盖时间约 16 秒，
  不是原先的约 4 秒。FPS 统计窗口不变。
- 分位数计算移到现有 500ms UI 更新节拍或 1s 上报节拍，
  不在每次呈现回调内反复排序所有延迟样本。
- 重连及组件清理重置限频状态，保留现有异常值、时钟同步和跨域失败处理。

## 验证

单元测试覆盖：日常模式限频、首帧采样、逐帧 FPS 统计、诊断逐帧读取、
重复印章去重、无印章回退、重连重置、指标上报及 UI 提示。
执行相关前端测试、类型检查及生产构建。

运行验证保持源 FPS、浏览器窗口可见性、窗口大小及显示刷新率一致：
逐帧诊断、日常 15Hz 抽样、关闭车端印章三组各观察至少 30 秒。
重启或重连后预热至少 20 秒，避免旧样本窗口污染。
记录浏览器回调 FPS、帧间隔 P95、接收 FPS 和丢帧计数；
可获取时对照浏览器 presentedFrames 增量，防止把回调漏采直接认定为显示丢帧。

目标为浏览器呈现接近 58～60fps；这是实验目标，不是补丁效果承诺。
显示 E2E 的前后精确比较使用相同逐帧诊断模式；抽样结果不直接与原先
首现分布做性能优劣结论。若只有关闭印章才改善，则记录测量扰动，
不将缺少精确 E2E 证据写成延迟改善。

## 范围与交付

仅触及前端视频 hook、对应测试以及必要的提示文本。
不加入硬编、120fps、Unity 调度改造或后端协议扩展。
实现完成后汇报测试结果、运行证据和剩余瓶颈。运行验证需要重启车端
时先确认，以免中断驾驶；不自动提交 Git。

## 自检

已明确采样偏差、窗口覆盖时间、统计口径和实验一致性。
无待定项。书面规范经用户审阅批准后再进入实现。

## 执行结果（2026-11-01）

- 日常像素读取按单调时钟限频至最多 15Hz，诊断模式逐帧读取。
- FPS 原始时间戳逐帧记录，分位数在 UI 刷新或上报时计算。
- 重连重置采样限频、去重和 FPS 窗口，避免前一会话污染。
- 提示文本明确抽样与诊断口径；有本地 E2E 样本时不误报“无 E2E”。
- 58 个前端测试文件、457 项测试全部通过；相关视频测试为 37 项。
- TypeScript 检查、变更文件 ESLint、生产构建及 git diff --check 通过。
