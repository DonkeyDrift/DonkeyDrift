# WebRTC 第二阶段：回调调度与呈现计数

## 基线与范围

2026-11-01 同一会话连续 15 秒：源约 60fps，浏览器回调 FPS
约 44～53，帧到达间隔 P95 约 22～24ms，实际编码约 3.5～6ms。
当前 browser_fps 根据回调次数计算，尚不能区分回调漏采与呈现提交不足。
此轮仅修改前端 hook、视频指标提示及测试；保留第一阶段未提交变更。
不改 TCP、Unity、码率、分辨率或控制链路，不创建 Git 提交。

## 方案与选择

推荐前端回调调度优化及计数对照。备选为事件驱动 TCP 接收或 Unity
捕获管线优化，但两者需要跨进程验证和车端重启，且现有证据不能定位根因，
本阶段不实施。无需视觉设计或布局修改。

## 设计

1. 回调入口记录测量时钟后，立即注册下一次 requestVideoFrameCallback，
   再执行印章读回及统计。每个入口只注册一次。清理仍取消最新回调句柄，
   避免重复回调链和卸载后继续采样。
2. 保留每次回调的 presentationTime 与 presentedFrames 对照窗口，最多
   120 个观测点。presentedFrames 表示浏览器已提交合成的累计帧数，
   不代表源内容唯一帧数、屏幕出光或硬件显示扫描次数。
3. presentedFrames 可用且计数、时间严格递增时，呈现 FPS =
   计数增量 / 时间增量；回调 FPS 仍按观测次数 / 时间增量独立计算。
   窗口中的漏采回调数 = 计数增量减去相邻观测次数，不称为源丢帧。
4. 元数据缺失、非有限值、非整数计数、计数或时间回退时重置对照窗口。
   至少两个有效点才能计算呈现 FPS；不足时回退现有回调 FPS。
   重连和清理同时重置窗口。
5. browserFps 及现有 browser_fps 上报优先使用呈现提交 FPS，
   浏览器不提供计数时保持原回调口径。不增加后端接口或协议字段。
   hook 本地 metrics 增加可选的 callbackFps、presentedFps、
   missedCallbacks，用于视频 FPS 提示及测试。
6. FPS 提示注明当前计数口径、回调 FPS、窗口漏采数量；
   不将校正后的较高 FPS 宣称为实际性能提升。
   帧间隔 P95 保持回调间隔含义，不冒充全部呈现帧的间隔分布。
7. 第一阶段的印章 15Hz 限频、逐帧诊断、240 样本 E2E 窗口、
   500ms UI 刷新和 1s 上报节流均保持不变。

## 验证与成功标准

单元测试覆盖：60 次呈现但 30 次回调的计数对照、元数据缺失回退、
计数重置、无效输入、窗口边界、提前注册顺序、卸载取消最新句柄、
重连窗口清理、FPS 提示和原 E2E 回归。
执行完整前端测试、类型检查、变更文件 lint 和生产构建。

软件验收：无重复回调链、无新增采样开销失控、旧浏览器回退正常，
指标正确区分提交计数与回调计数。可提供时保持前台页面同条件记录
至少 30 秒的计数及 E2E。不得用 FPS 口径变更宣称帧率提升；
只有相同模式、同条件的 E2E 或回调漏采对照才用于性能结论。

运行验证不主动接管当前驾驶会话，不重启车端或模拟器。
若无法采集计数对照或会话切换，明确标记性能验收未完成。
