# RFC：第三视角俯拍漂移控制系统

- 日期：2026-08-29
- 状态：已评审通过（与需求方逐节对齐），待实施
- 阶段：方案 C 第一阶段

## 1. 背景与问题

车载视角的自动驾驶漂移（摄像头 + 陀螺仪 → tub → 训练 rnn/imu 系列 pilot）效果不理想，具体症状：

1. 模型能控制车正常行驶，但始终进入不了漂移状态；
2. 能起漂但保持不住，数秒内甩尾/spin out；
3. 录制数据质量与轨迹存在问题。

已验证的关键事实：`docs/Rfc/auto-drift-replay.md` 的漂移回放方案（绕开模型，回放人工操作给 ESP32）**试过且有效**——说明执行链路（指令 → ESP32 → 车辆机械响应）与人工漂移数据本身是好的，瓶颈在"模型决策"环节。

根因分析：漂移的核心状态量是**侧滑角 β**（车身朝向与运动方向的夹角）。车载视角下画面随车身剧烈旋转横移，β 在画面中几乎不可观测，模型"看不到自己滑到什么程度"，自然无法保持。另有代码层面疑点：模板 `HAVE_IMU` 默认 `False`（`donkeycar/templates/cfg_complete.py:615`），实际录制的 tub 大概率未含 IMU 字段，imu 系列模型可能从未吃到陀螺仪数据。

## 2. 方案选型结论

三个候选（共用同一条俯拍数据管道）：

| 方案 | 核心思路 | 结论 |
|---|---|---|
| A：第三视角端到端行为克隆 | 沿用 donkeycar 范式，车载 cam 换俯拍 cam | 改动最小，但行为克隆的开环模仿本质在失稳平衡任务上仍会滚雪球，未解决"缺闭环反馈"根因 |
| B：状态估计 + 经典反馈控制 | 俯拍解位姿 → β + 陀螺仪横摆角速度 → 级联 PID | 对症"保持不住"，可解释可调参，数据量要求低 |
| **C（选定）：B 先行 + 学习留门** | 先用 B 打下"定圆漂 30 秒"，同步录制数据集照建，为后续模仿学习留接口 | 见效概率最高，每步可验证 |

## 3. 需求约束（与需求方对齐结果）

- 俯拍相机：USB 外接相机（三脚架约 2m 高，俯拍约 2m×2m 场地）
- 笔记本：RTX 4060，负责视觉、控制、录制与（后续）训练
- 车端 Linux 上位机（SBC）**保留**，仅作桥接：笔记本 ⇄ WebSocket ⇄ SBC ⇄ 串口 ⇄ ESP32
- 人工操控一律使用 **RC 遥控器**（接收机直连 ESP32，ESP32 本地解析执行；不通过笔记本网页开车）
- 车载摄像头与第一视角 WebRTC 保留（操作者观察用），车载 tub 录制能力留作对照实验
- ESP32 固件已有一个**基于横摆角速度的转向修正程序**（Drift Assist 类，遥测疑似对应 `dsc` 字段），有配置开关可关
- 人工漂移的油门操控是**点动（脉冲）模式**而非连续量：点动频率越高车身自旋越强、越容易飘小弯；频率越低越容易飘大弯——本质是通过油门脉冲周期性打破后轮摩擦平衡来控制横摆力矩。点动**幅值同步在调**，且**转向同步微调**（双通道耦合操控，详见 7.3 节）
- 采样率事实（已核实，`Firmware/MUS4_FW/MUS4_FW.ino:729-741`）：T 帧（RC 实际油门/转向）**60Hz 且仅 MANUAL 模式发送**；$IMU 100Hz 全模式；下行 `t:s` 控制帧由 SBC 主循环 60Hz 写入且无滤波——上下行链路均足以忠实承载人手点动（约 1~10Hz）波形
- 第一阶段成功标准：人工 RC 起漂后控制器接管，定圆连续漂移 ≥30 秒不甩尾

## 4. 总体架构与分阶段控制流

控制权状态机直接映射固件现有 MODE 0/1/2 机制，不新造仲裁协议：

```
阶段1 人工起漂（MODE 0 MANUAL）
  人操作 RC 遥控器 → 接收机直连 ESP32 → ESP32 解析后直接驱动舵机/电调
  （控制回路完全在车端本地，不经笔记本、不依赖 WiFi）
  笔记本侧：DriftVision 只观察——实时解算位姿与侧滑角 β
  注：起漂阶段用 MANUAL 而非 SEMI，原因有二：①固件 T 帧（RC 油门/转向）
  仅在 MANUAL 模式 60Hz 上传，阶段 1~2 的观察与录制都需要 RC 波形；
  ②SEMI 模式下固件 ControlMixer 会把修正量叠加进实际输出，污染人工输入的纯度

阶段2 自动接管（MODE 2 FULL_AUTO）
  笔记本检测到 |β| 超阈值且持续稳定（如 >15° 保持 500ms）
  → 下发 MODE 2（MODE 0→2 直接跳变，固件接受性为实施核对项）
  → 控制器以 60Hz 经 ws→SBC→串口下发 angle/throttle（油门为脉冲发生器输出，见 7.3）
  → ESP32 忽略 RC 油门/转向，执行笔记本指令；T 帧停发（RC 已无控制权，不影响）

阶段3 退出/夺回
  看门狗（丢帧>200ms / ws 断线 / β 失稳）→ 下发 Park / MODE 0 交还人工
  RC CH4 拨杆随时物理夺回（固件最高优先级，不依赖任何软件）
```

笔记本端新增组件（`web_ui/backend/`）：

| 组件 | 职责 |
|---|---|
| `drift_vision.py` | USB 相机采集（OpenCV，30/60fps 可配）、AprilTag 检测、单应性映射到场地坐标，输出车位姿 (x, y, heading) |
| `drift_controller.py` | 状态融合（β 估计）+ 级联 PID + 限幅/看门狗 |
| `sync_recorder.py` | 三路数据同步录制（详见第 6 节） |
| `routers/drift.py` | Drive 页"第三视角漂移"卡片 API |
| `DriftSession` 状态机 | `IDLE → CALIBRATE / RECORD / AUTO` |

车端代码零改动：笔记本控制器作为"虚拟驾驶员"经现有 `/api/drive/ws` client 通道下发，与现有浏览器控制同构。实施时需核对现有服务端多 client 并存行为，确保 AUTO 期间浏览器不并发发送控制字段（UI 上禁用）。

## 5. 状态估计

- **位姿**：车顶贴 AprilTag，每帧解出 (x, y, heading)，经单应性映射到场地坐标（米制）
- **侧滑角 β**：β = 车身 heading − 航迹切线角；航迹角由位姿序列差分（低通滤波）得到；与陀螺仪横摆角速度做互补滤波降噪（位姿差分低频可靠、IMU 高频可靠）
- **横摆角速度 r**：优先用陀螺仪 `imu/gyr_z`（$IMU 100Hz，延迟低于视觉）

## 6. 数据管道与时间对齐

录制（RECORD 模式，控制来自 RC，笔记本只录）：

- **数据源三路**：
  1. 笔记本相机帧（笔记本时钟戳 t_cam + 俯拍图像 + 位姿）
  2. 车端遥测（均源自 ESP32 解析，经串口→SBC→ws 到达，带到达时间戳与固件 ts_ms）：rc/steering、rc/throttle（60Hz，仅 MANUAL）、imu/*（100Hz 全模式）
  3. 由上两者派生：state/beta、state/yaw_rate，以及**油门点动特征**（见下）
- **对齐方法**：以 t_cam 为基准对遥测流线性插值，目标对齐误差 <10ms
- **格式**：复用 tub v2 格式，笔记本端写入，字段：`overhead/image_array, pose/x, pose/y, pose/heading, state/beta, state/yaw_rate, state/throttle_pulse_freq, state/throttle_duty, state/throttle_pulse_amp, rc/steering, rc/throttle, imu/gyr_x..z, imu/acl_x..z`——Web UI Tub 管理页直接可见
- **油门点动派生特征**：对 rc/throttle 滑动窗（约 1s）在线/离线提取——点动频率（过零/峰检测）、占空比（油门高于阈值的时间占比）、脉冲峰值幅值。60Hz 采样对人手 1~10Hz 点动波形充分，波形不欠采样；辅助校验信号为 imu/acl_x（每次点动的纵向冲击，100Hz）与 imu/gyr_z（自旋响应，100Hz）
- **用途**：控制器调参、离线回放仿真、后续模仿学习数据基础

## 7. 控制器设计与固件 yaw-rate 修正的处置

### 7.1 固件修正冲突的决策（单一闭环原则）

ESP32 现有基于横摆角速度的转向修正与笔记本控制器内环（横摆角速度跟踪）**目标完全重叠**——两个闭环叠在同一执行器（转向舵机）上，固件修正对笔记本环是不可预知扰动，两环增益叠加、相位不匹配时互相拉扯甚至振荡。决策：

- **第一阶段：FULL_AUTO 下经配置关闭固件 yaw-rate 转向修正**，笔记本 PID 是唯一转向闭环，先调稳主回路、拿到定圆 30 秒基线
- **第二阶段（可选）**：若实测存在高频抖动需要更快的阻尼，再将固件修正作为高频内环受控引入，前提：开关可控、修正量进遥测可观测（核实 `dsc` 字段即此修正量）
- **澄清既有疑点**：本方案的 imu 数据取自 100Hz ws 遥测（`SyncRecorder` 在笔记本端写入），不依赖车端 `HAVE_IMU` 开关；`HAVE_IMU` 仅影响车端自己的 tub 录制（第 12 节对照实验用，届时在车端开启）

### 7.2 控制器结构（初版，增益全部 Web UI 可配）

- **外环（慢，5~10Hz 更新）**：目标侧滑角 β*（初值 25°）+ 定圆半径保持（圆心距误差）→ 输出两类调节量：转向偏置、**油门脉冲参数**（频率/占空比/幅值/基础油门，见 7.3）
- **内环（快，60Hz）**：横摆角速度跟踪 → 转向连续微调；油门脉冲发生器按当前参数生成瞬时油门序列
- **保护**：
  - 输出限幅（映射到现有 ±100 串口协议）
  - **delta 限幅**（转向变化率限制，补偿固件无 slew 限幅的缺口，`auto-drift-replay.md:66` 已识别）
  - 看门狗：丢帧 >200ms / ws 断线 / 控制器异常 → 下发 Park + 切 MODE 0
- **起漂**：第一阶段由人 RC 手动起漂（阶段 1→2 状态机），全自动起漂留作后续迭代

### 7.3 油门点动（脉冲）控制

**机理**（人工经验 + 摩擦圆模型）：漂移中后轮已处于大滑移状态，油门脉冲使后轮纵向滑移率周期性突破摩擦圆上限——纵向力挤占侧向抓地（摩擦圆耦合），每"点"一次产生一次横摆力矩脉动。**点动频率高** → 单位时间抓地丢失事件密度大 → 平均后轮侧向力更低 → 自旋倾向强 → 飘小弯；**频率低** → 后轮有更多时间恢复部分抓地 → 飘大弯。即点动频率是一个等效的"平均后轮侧向抓地"调节量，比连续油门多出一个独立的控制自由度；人工实操中**幅值与频率同时调节，且转向同步微调**——是双通道耦合操控，不是"转向稳住只点油门"。

**控制器侧实现：油门脉冲发生器（Throttle Pulse Generator）**

```
外环（慢）: β/半径误差 → 脉冲参数 (f 频率, D 占空比, A 幅值, T_base 基础油门) + 转向偏置
发生器（快, 60Hz tick）: 按当前参数生成瞬时油门 u(t)：
  高电平段: throttle = T_base + A
  低电平段: throttle = T_base
  相位由内部时钟维护，参数变更时平滑过渡（避免半周期突变）
下行: 60Hz ws → SBC 串口 t:s 帧 → ESP32 执行（链路无滤波，波形不失真，已核实）
```

- 转向通道保持连续输出（人工的"同步微调"对应外环的转向偏置 + 内环的 yaw-rate 反馈），两通道由**同一个外环协调**，不做独立解耦
- 脉冲参数的初值不拍脑袋：从录制的人工数据离线拟合"脉冲参数 ↔ 实际轨迹半径/β"映射（见下），作为外环增益与参数表初值

**数据侧配套**：

- SyncRecorder 在线提取点动派生特征进 tub（`state/throttle_pulse_freq/duty/amp`，见第 6 节），人工数据自动带标注
- 离线标定工具（scripts/）：对人工漂移 tub 做滑动窗分析，输出"点动频率-半径""占空比-β"关系曲线与拟合参数表，用于控制器外环整定，同时**验证机理建模**（数据上应呈现"频率高→半径小"的单调关系，若不成立则回头修正模型）

**对学习路线（第二阶段）的意义**：模仿学习可直接学瞬时油门序列（RNN 时序模型隐式包含点动），也可结构化输出脉冲参数（维度低、易学、可解释）；点动派生特征可作辅助监督信号。本阶段的录制数据与特征提取对两条路线通用。

## 8. 标定流程（一次性，Web UI 提供入口）

1. 相机内参标定（棋盘格，标准 OpenCV 流程）
2. 图像↔场地单应性（地面四角已知点 + 圆心标记）
3. 车顶 AprilTag 尺寸登记
4. 标定结果存文件，可随时重标

## 9. 安全设计

- RC CH4 拨杆物理夺回：固件最高优先级，不依赖笔记本/网络（现有能力）
- 笔记本看门狗：视觉丢帧、ws 断线、控制器异常 → Park + MODE 0
- 指令限幅 + delta 限幅双保险
- Web UI 急停按钮（沿用 Drive 页现有机制）
- 人工控制永远不经笔记本：起漂阶段控制回路在车端本地，WiFi 故障不影响人工驾驶

## 10. 测试与分步验收（每步通过才进下一步）

1. **链路实测（第一验收项）**：端到端延迟（相机曝光→指令到车）与三路数据对齐精度；P95 延迟预算 ~100ms，超标则加超前补偿或降档再评估
2. **单元测试（TDD）**：β 计算、遥测插值对齐、PID 输出与限幅、**脉冲发生器波形与参数平滑过渡**——用录制数据回放做 fixtures
3. **点动机理验证（离线）**：对人工漂移数据做"点动频率 ↔ 轨迹半径/β"相关性分析，确认"频率高→小弯"在数据上成立——机理不成立则先修模型再调控制器
4. **离线仿真**：用人工漂移的位姿序列回放，闭环跑控制器逻辑（含脉冲发生器）
5. **实车低速闭环**（非漂移，定圆普通行驶）验证控制器基本稳定
6. **最终验收**：RC 起漂 → 接管（脉冲发生器重现人工点动模式）→ 定圆连续漂移 ≥30 秒

## 11. 风险与开放问题（实施中逐项验证，不假设通过）

| 风险 | 应对 |
|---|---|

| 1080p60 相机 USB 带宽 | 需 USB3/MJPEG；不行则 720p60 或 1080p30 |
| β 估计噪声 | 互补滤波；仍不行则加重 IMU 权重或提高帧率 |
| 车顶标签安装牢固度 | 漂移离心力下不移位；机械固定方案在标定阶段确认 |
| 服务端多 client 并发控制字段 | 实施时核对 `web_ui/backend/routers/drive.py` 现有行为，AUTO 期间 UI 禁用浏览器控制 |
| `dsc` 遥测字段语义 | 实施时核对固件，确认是否为 yaw-rate 修正量（关系第二阶段可观测性） |
| MODE 0→2 直接跳变的固件接受性 | 阶段 1→2 切换走 MODE 0 直接下 MODE 2，实施时核对固件状态机（不经过 SEMI） |

| 点动低电平段的基础油门 T_base | 人工"松油门"瞬间是否归零或保持少量油门，从录制波形实测确定，不假设 |
| 无俯拍形态的 β 估计精度 | 编码器路线已被"全轮打滑"硬件事实否决，主路线为俯拍金标准蒸馏（12.2 节）；其精度由俯拍阶段消融实验量化，不满足控制需求则评估轻量外部基准 |
| 车载摄像头规格未定 | 型号/分辨率/帧率/快门类型（卷帘/全局）待确认，影响视觉里程计前端参数与运动模糊风险（12.3 节） |

## 12. 演进路线与资产迁移（无第三视角的远期形态）

本方案在长期路线中的定位：**不是绕开车端问题的弯路，而是把车端问题拆成三步——可观测性由俯拍解决、控制律与视角无关、最后用蒸馏把可观测性也搬回车端。**

### 12.1 资产迁移清单

| 资产 | 迁移性 | 说明 |
|---|---|---|
| 控制律（β/半径外环 + yaw-rate 内环 + 油门脉冲发生器） | 完全迁移 | 控制律是车辆动力学的函数，不是视角的函数；点动机理（摩擦圆耦合）与相机位置无关 |
| 点动特征提取 + 同步录制数据管道 | 完全迁移 | 作用于 rc 波形与 IMU 时序，与图像无关；车端 tub 可直接叠加同字段 |
| β 估计方法论 | 迁移（见 12.2） | 运动学约束与锚定思想不变，传感器源更换 |
| 训练经验 | 直接复用 | 车载方案失败根因（β 不可观测、IMU 未进 tub）已有系统解法：未来车载模型应输入状态量、输出结构化脉冲参数 |
| 分步验收/延迟实测/机理验证 | 通用方法 | 与视角无关 |
| AprilTag/单应性标定基建 | 不迁移但有第二职业 | 车端方案开发期当**评估裁判**（毫米级量化车端 β 估计误差），相当于人形机器人领域的动捕 |

### 12.2 无俯拍的 β 估计：主路线与已否决路线

**物理基础（运动学恒等式，不依赖轮胎模型）**：β̇ = r − a_y/v。β 的短时变化量由陀螺仪（r，IMU 中最准的量）与侧向加速度推出；绝对值靠锚定段（起漂前直行 β≈0 天然重置）。高频可靠是物理保证，绝对精度是实验结论——由俯拍金标准量化。

**已否决**：轮速编码器（硬件事实：漂移时**全部车轮打滑**，任何轮的编码器读数都是轮速虚高，不等于车速）；纯加速度计积分速度矢量（零偏+重力泄漏+振动积分，秒级到十几秒级发散——1° 姿态误差即泄漏约 0.17 m/s² 假加速度，漂移姿态剧烈时更甚）。

**主路线：俯拍金标准蒸馏（teacher-student）**

```
俯拍阶段：同步录制配对样本 (IMU 六轴 + RC 输入, 俯拍 β 真值)
离线训练：估计器 f: (IMU 序列, RC 输入 [, 车载视觉里程计特征]) → β
部署：车端只跑 f，输出 β 喂给同一套控制律
```

漂移是准稳态受控机动，点动油门与横摆/侧向加速度模式同 β 之间存在稳定动力学映射——解析建模难，但可学习；运动学方程作为模型的归纳偏置（特征构造或物理一致性损失）。车载摄像头（现成硬件）的单目视觉里程计可作为可选输入增强速度矢量的短期观测（漂移图像的横移+旋转光流模式与侧滑强相关）。

**俯拍阶段的关键消融实验（决定远期路线的数据）**：量化三档输入下的 β 恢复误差——① 仅 IMU+RC；② +车载视觉里程计特征；③ 俯拍全量（对照上界）。若 ①/② 档误差不满足控制需求（阈值随控制器整定确定），则远期备选轻量外部基准（如 UWB，另行立项评估），不在本 RFC 范围。

**诚实的不确定性**：此路线的精度风险高于"编码器+IMU"类方案（该类已被全轮打滑事实否决），蒸馏估计器的绝对精度、漂移特性（长时间无锚定段）均需实验定量；这也是 12.1 中"评估裁判"基建保留价值的原因。

### 12.3 视觉里程计增强的具体技术路线

**定位刻意收窄：不做完整 VO/SLAM，只做"车身系速度方向观测器"。** 完整视觉 SLAM 在漂移车上既不必要也跑不动；β 估计只需要 30Hz 的速度方向这一个自由度。

```
车载相机（前视，30fps）
  ↓ 灰度化 + 降采样（~320×240）
  ↓ Shi-Tomasi 角点 + 金字塔 LK 光流（OpenCV 现成）
  ↓ 帧间运动分解：旋转分量 ↔ 与陀螺仪互校验；平移方向（车身系单位矢量）← 只取这个
  ↓ 30Hz 输出"车身系速度方向"观测 → 蒸馏估计器的可选输入
```

算力：LK 光流在 320×240 上每帧毫秒级，车端 SBC CPU 可与 drive loop 共存。

**为什么该用途避开了单目 VO 的两个经典死穴**：
1. 单目平移**尺度不确定**（up-to-scale，教科书结论）——但 β 只需要速度**方向**，尺度漂移不影响方向；
2. 传统 VO 误差随里程**累积**——但此处每帧独立估计瞬时方向、不积分，无累积漂移。本质是"电子风速计"（只回答现在往哪走），不是里程计。

场景加成：漂移时横移+旋转剧烈，恰是运动可观测性最好的情形（纯前向直线才是 VO 退化情形）；相机离地近、视差充足。工业同构参照：微型无人机下视光流测速（PX4FLOW）为量产方案——"看地面测速度、不受执行器打滑影响"。极简硬件替代（可选）：下视激光鼠标传感器（RC 圈成熟玩法，几美元），同样免疫车轮打滑，可作编码器的现成替代。

**风险与对策**：运动模糊（横移快+曝光长→特征退化；对策：锁短曝光 <5ms、提帧率、多帧融合）；地面低纹理（对策：铺纹理垫，漂移胎痕本身即纹理）；卷帘快门在快速旋转时的帧内畸变（严重时换全局快门相机，几十美元级）；车载摄像头规格（型号/分辨率/帧率/快门类型）**待确认**，为实施核实项。

**架构兜底**：本增强在消融实验中为中间档（① 仅 IMU+RC → ② +视觉里程计 → ③ 俯拍全量对照），实际误差由俯拍金标准量化，②相对①无显著收益则移除，主线无损。
