第 1 章 · 一页看懂 DonkeyDrift

如果把一辆 RC 漂移车比作驾校里的学员，那么 DonkeyDrift 就是坐在副驾的教练 + 大脑：它是一段跑在车上（或连着车的电脑）的 Python 程序，负责看路（读相机画面）、记笔记（把每一次驾驶录成数据）、练本领（用数据训练 AI 模型）、下指令（算出转向和油门发给小车）。而真正握紧方向盘、踩下油门的"手"，是另一块叫 MUS4 的 ESP32 固件——它有自己 的配套科普页（Firmware/MUS4_FW/docs/architecture-guide.html）专门讲它。本章先用一张图看清整个系统谁管什么。

它为什么叫「大脑 + 驾校」？普通遥控车的大脑是你的手——遥控器直接连舵机。DonkeyDrift 在中间加了一层"会学习的教练"：你先手动开车，它把每一帧画面和你当时的转向、油门一起记进一个叫 Tub 的数据集（类似驾校的行车记录仪 + 教练笔记）；然后用这些数据训练一个 AI 模型，相当于让教练"刷题"总结你的开法；最后把模型装回车上，它就能自己看画面、自己打方向了。这条"录数据 → 训练 → 自动驾驶"的流水线，正是 DonkeyDrift 从 Donkeycar 继承来的看家本领（见 README.md 的 Quick Start）。

拆开大脑：传送带 + 共享白板。DonkeyDrift 的核心是一台叫 Vehicle 的"传送带" （donkeycar/vehicle.py:151 的主循环，默认每秒转几十圈）。传送带上挂着一个个部件（Part）——相机部件、控制器部件、AI 推理部件、串口部件……每个部件像一块乐高积木，只管一件事：从一块"共享白板"上读出自己需要的输入，算完再把结果写回白板。这块白板叫 Memory（donkeycar/memory.py:9），就是一个键值字典，比如相机部件写入 cam/image_array，AI 部件读出它、写入 pilot/angle，驾驶模式部件再决定听人还是听 AI（donkeycar/templates/complete.py:485 的 DriveMode）。车辆模板 donkeycar/templates/complete.py 就是默认的"接线图"：从 complete.py:88 创建 Vehicle 开始，一路 V.add(...) 把几十块积木装好，最后 complete.py:620 启动主循环。

上位机与 MUS4 固件的分工：教练与手。为什么算出来的油门转向不直接发给电机？因为"聪明"和"快且可靠"很难兼得。于是系统把活儿劈成两半：

上位机 DonkeyDrift：管「智能和体验」

  • 看路：读相机、IMU 等传感器数据
  • 学习：录制 Tub 数据、训练 TensorFlow / PyTorch 模型
  • 决策：AI 推理出转向 / 油门（-100~100 的百分比值）
  • 体验：提供浏览器驾驶界面、校准和训练面板

MUS4 固件（ESP32）：管「安全和实时」

  • 执行：以 300Hz PWM 精确驱动舵机和电调
  • 安全：Park 停车、PWM 限幅、失效保护，随时可接管
  • 桥接：读取原车 RC 遥控器输入，人永远能抢回方向盘
  • 上报：把车身状态持续回传给上位机

两半之间靠一根串口（USB/串口线）对话，说的"暗号"是几行短小文本帧：上位机下行的是 油门:转向 形式的 PWM 命令（donkeycar/parts/actuator.py:1507 写入串口）；固件上行的是遥测——T<t>S<s> 报告当前 RC 油门/转向、M<m>:P<p> 报告驾驶模式和 Park 状态、$IMU,... 报告惯性传感器读数 （解析逻辑见 actuator.py:1285 与 actuator.py:1325）。就算上位机的 Python 程序卡住了，固件也会立刻接管并把车停稳——这正是"安全交给固件"的意义。

浏览器是怎么进来的？你不用守着车敲命令。DonkeyDrift 自带一个 Web UI：后端是 FastAPI（默认端口 8000），把配置、Tub 数据、训练、驾驶等功能挂成 /api/config、/api/tub、/api/trainer、/api/drive 等路由（web_ui/backend/main.py:40-46）；前端是 React 页面。车上的主程序通过一个 DriveApiBridge 部件 （complete.py:759）连上后端的 WebSocket，于是你在浏览器里就能看车载画面、转方向盘、切 AI 模式、点"开始训练"——浏览器成了这套系统的遥控器加大屏幕。

一句话总结：MUS4 固件是忠实可靠的"手"，毫秒级执行、永远把安全放第一；DonkeyDrift 是会学习的"大脑"，管看路、记数据、练 AI；Web UI 则是你和大脑对话的窗口。后面的章节会分别深入这三块：先看清主循环和数据怎么流动，再看 AI 怎么训练出来，最后看固件如何守住安全底线。

第 2 章　Vehicle + Memory + Part：乐高式流水线

打开 DonkeyDrift 的上位机代码，你会发现整辆小车的"大脑"其实只有三个角色：Vehicle 是一条永不停歇的传送带， 每转一圈就依次请每个工人干一次活；Memory 是车间中央的一块共享白板，谁有了新数据就写上去，谁需要数据就去读； Part 则是一块块乐高积木——相机、AI 飞行员、舵机驱动，各自只关心自己的一亩三分地。 神奇之处在于：积木之间从不直接说话，所有交流都通过白板上的"字符串键"完成，比如 'cam/image_array'（相机拍的最新一帧画面）、 'user/steering'（人打的方向）。这意味着你可以随时拔掉一块积木、换上另一块，只要它读写的键不变，整条流水线照常运转。

Vehicle：传送带

start(rate_hz=20) 一调用，传送带就开动了：先唤醒所有"住"在独立线程里的部件 （vehicle.py:141），然后进入 while self.on 无限循环（vehicle.py:151）。 每一圈，update_parts()（vehicle.py:186）按添加顺序遍历所有积木：从白板读出它的 inputs、 调用它的 run()、把返回值写回白板（vehicle.py:204 / vehicle.py:213）。 一圈干完还有剩时间就小睡一会儿，保证每秒刚好转 rate_hz 圈。

Memory：共享白板

Memory 朴素得令人意外——它就是对 Python 字典的一层薄包装（memory.py:9）。 put(keys, values) 把数据写上白板（memory.py:35），get(keys) 按键读回来 （memory.py:49），找不到就返回 None。没有锁、没有队列、没有消息协议， 因为每圈里同一时刻只有一个零件在读写，简单反而可靠。

Part：鸭子类型积木

想当一块积木不需要继承任何基类——"鸭子类型"的意思是：只要它走起来像鸭子，它就是鸭子。 实现 run() 就能上车；想常驻后台就实现 update() 并以 threaded=True 注册，Vehicle 会为它单独开线程（vehicle.py:102）， 之后每圈改调 run_threaded()；停车时若实现了 shutdown() 还会被温柔地收尾 （vehicle.py:221）。Vehicle.add(part, inputs=[...], outputs=[...]) （vehicle.py:72）就是那把"接线枪"。

这套接线在真实车辆模板里长什么样？打开 donkeycar/templates/complete.py：相机被注册为线程部件， 每圈把最新画面写上 'cam/image_array'（complete.py:962）；AI 飞行员以图像为输入、 输出 'pilot/angle' 和 'pilot/throttle'，并且带着 run_condition='run_pilot' — 只有白板上这个开关为真时才干活（complete.py:426）；接着 DriveMode 像驾校教练一样在"人的指令"和 "AI 的指令"之间二选一，写下最终的 'steering' 和 'throttle'（complete.py:485）； 最后 TubWriter 把画面和操控记录存盘，供日后训练（complete.py:578）。整张"电路图"全是 V.add(...) 一行行声明出来的，没有一处部件之间直接调用。

为什么老司机们钟爱这种设计？因为改车就像换积木。想把真实相机换成模拟器？换一个输出同样叫 'cam/image_array' 的部件即可，下游的 AI 飞行员毫无察觉。想在 AI 和电机之间插一个"看到停车标志就刹车" 的零件？模板里现成的 StopSignDetector 读 'pilot/throttle'、改写后再写回同名键 （complete.py:458），像乐高一样插在中间就行。甚至打印一个按钮事件也是一块积木——Lambda 部件配上 run_condition，按钮按下那一圈才执行（complete.py:161）。

小思考：Memory 白板上后写的数据会覆盖先写的，这正好符合"开车只关心最新一帧"的直觉； 但也意味着两个部件不能同时往同一个键上写不同意思的数据——所以模板里才有 DriveMode 这样的"仲裁员"， 统一决定最终指令，而不是让人和 AI 抢方向盘。

第 3 章 · parts/ 部件大观园：一盒 60+ 块的乐高

打开 donkeycar/parts/ 目录，你会看到 60 多个 Python 文件——这就是 DonkeyDrift 的「零件盒」。上一章说过，整辆车由 Vehicle 传送带和 Memory 共享白板驱动；而零件盒里的每一块积木（叫「部件」，Part）都只干一件小事：摄像头只负责拍照，舵机只负责转角度，记事本只负责把数据写进硬盘。它们长得五花八门，但接口完全一致——声明「我要读白板上的哪几个格子」和「我会往哪几个格子写东西」，然后用 V.add(部件, inputs=[...], outputs=[...]) 往传送带上一卡（templates/complete.py:150），就开始工作了。需要哪块拿哪块，不需要的就留在盒子里，这就是「按需取用、即插即用」的乐高哲学。

按职能可以把这盒积木分成六堆，每堆选一个代表认识一下：

  • 眼睛：camera.py 里住着一排相机——树莓派相机的 PiCamera（camera.py:23）、普通 USB 摄像头的 Webcam（camera.py:85），甚至还有一块「假相机」MockCamera（camera.py:333），专门在没有真相机时生成测试图片。想要深度视觉或环视，还有 realsense2.py、oak_d.py 和激光雷达 lidar.py 可选。
  • 手脚：actuator.py 是执行机构大本营，PWMSteering（actuator.py:284）和 PWMThrottle（actuator.py:333）把白板上「转向 0.3、油门 0.2」这样的数字翻译成舵机和电调听得懂的 PWM 脉冲；更底层的引脚操作则抽象在 pins.py（如 pins.py:563 的 PCA9685 驱动）里。
  • 大脑：keras.py 里整个 KerasPilot 家族（keras.py:45）都是「驾校学成归来」的神经网络驾驶员，PyTorch 党去 pytorch/（如 pytorch/ResNet18.py:29），fastai 党用 fastai.py 的 FastAiPilot（fastai.py:40）。三派统一由 interpreter.py 的 Interpreter（interpreter.py:76）封装推理，还支持 TfLite（interpreter.py:250）和 TensorRT（interpreter.py:299）加速——换个框架，传送带上的接口纹丝不动。
  • 记事本：你开车时它默默把「看到什么 + 怎么打的方向」一对对记下来，这就是训练数据的来源。老版 datastore.py 的 Tub（datastore.py:22）已升级为 v2：datastore_v2.py 用 Manifest（datastore_v2.py:220）做可追加、可断点续写的数据清单，运行时实际挂上车的是 tub_v2.py 的 TubWriter（tub_v2.py:119）。
  • 对讲机：serial_port.py 的 SerialPort（serial_port.py:13）负责和 MUS4 固件那头的 ESP32 聊串口；network.py 提供 ZMQ（network.py:6）、UDP、TCP、MQTT（network.py:305）一整套网络收发；telemetry.py 的 MqttTelemetry（telemetry.py:24）把车辆状态广播出去；auth_part.py 的 AuthPart（auth_part.py:41）则是身份识别门卫，确认「你是我家固件」才放行。
  • 仪表：imu.py 的 IMU（imu.py:9）报姿态和加速度，encoder.py 的 ArduinoEncoder（encoder.py:25）数轮子转了几圈，gps.py 报经纬度，odometer.py 的 Odometer（odometer.py:7）算里程——漂移车要知道自己「跑多快、往哪倾」，全靠它们。

为什么说像乐高？因为部件之间从不直接互相认识。相机不知道舵机的存在，神经网络也不关心图片是相机拍的还是 MockCamera 画的——它们只认白板上的格子名（比如 cam/image、angle、throttle）。这种「只认格子不认人」的设计（鸭子类型：会跑就行，不管你是谁）带来两个超能力：一是随便替换，把 PiCamera 拔了换 Webcam，下游部件毫无察觉；二是容易测试，用 Mock 部件就能在没有硬件的笔记本上把整辆车的数据流跑起来。

「按需取用」则体现在车辆模板里：启动脚本并不是把 60 个部件全挂上，而是按配置挑着装——templates/complete.py 里 add_camera(V, cfg, camera_type)（templates/complete.py:116）会根据你的 cfg 配置决定实例化哪一种相机（templates/complete.py:877 起的一串分支）。装激光雷达？改一行配置，模板就把 lidar 部件挂上传送带（templates/complete.py:125）。不装？它连内存都不占。零件盒满满当当，但真正上车的只有你需要的那几块。

小思考：零件盒里还有 fps.py（帧率统计）、led_status.py（状态灯）、voice_control/（语音控制）这类「非必需但好用」的配件。下次看 parts/ 目录时，不妨猜一猜每个文件属于上面哪一堆——猜对了，你就已经读懂这套架构了。

第 4 章 从数据到 AI 司机：Tub v2 → pipeline → 模型

前面几章里，车会跑、会看、会听话，但它还不会"自己开"。这一章讲的就是 DonkeyDrift 怎么把一个人的驾驶技术"教"给 AI。整个过程和驾校学员跟教练学车一模一样：学员先坐在副驾驶看教练怎么开（录数据），然后自己反复练习（训练），最后考下驾照独立上路（模型上车推理）。更妙的是，AI 上路后还能继续录数据、继续练，越开越聪明——这就是本章的环形闭环。

第一步：看教练怎么开（录数据）。你拿着遥控器开车时，车上的 TubWriter 部件（donkeycar/parts/tub_v2.py:119）就像一台"行车记录仪 + 动作捕捉器"：主循环每转一圈，它就把当前相机画面和这一刻你打的方向、油门数值打包成一条记录（record），写进名叫 Tub v2 的数据集。图片存成 jpg 文件，数值和时间戳写进清单（manifest），见 tub_v2.py:38-82 的 write_record()。开上十几分钟，就攒下几千条"画面 → 操作"的对照样本——相当于学员脑子里记下的"看到这种弯道，教练是这样打方向的"。

第二步：反复练习（训练）。录够了数据，在电脑上运行 donkey train --tub ./data --model ./models/mypilot.h5 命令（子命令定义在 donkeycar/management/base.py:547），它会把活儿交给 donkeycar/pipeline/training.py 的 train() 函数（training.py:111）。这个"总教练"做三件事：先用 TubDataset 把记录全读出来，按 train_test_split 分成"练习题"和"模拟考卷"两份（training.py:134-138）；再用 BatchSequence 把数据一条一条喂给神经网络（training.py:33）；喂之前还会经过 ImageAugmentation 做数据增强（training.py:49，实现在 pipeline/augmentations.py:14）——随机调亮度、加模糊，好比教练故意带你在阴天、黄昏练车，防止你只会在大晴天开。底层用的是 TensorFlow（Keras），也支持 PyTorch 框架（base.py:581-588）。

第三步：拿到驾照（产出模型）。训练结束后会得到一个模型文件，比如 pilot_25-01-01_0.h5——这就是 AI 的"驾照"，里面存着它学到的全部驾驶经验。系统还会顺手把它转换成更轻量的 .tflite 格式，方便在小算力的车机上跑（training.py:200-202）。同时，PilotDatabase（donkeycar/pipeline/database.py:17）扮演"车管所档案管理员"，把这次训练用了哪些数据、最终误差（loss）多大、什么时间练的，都登记进 database.json，训练误差曲线还会单独存一份 _meta.json 给 Web UI 画图（training.py:178-192）。

第四步：AI 上路（模型推理）。把模型文件交给车，车辆模板里的代码会用 get_model_by_type 造出一个 KerasPilot 部件并加载模型（donkeycar/templates/complete.py:319、complete.py:288）。所谓推理（inference），就是模型不再学习，只做"看图 → 给答案"：主循环每拍到一帧画面，它就输出一个转向值和一个油门值，像一位不知疲倦的司机。关键设计是：TubWriter 此刻仍在工作——AI 开车时你随时可以接管纠正，这些"纠错示范"又被录成新数据，喂回第二步继续训练。飞轮转起来，这就是闭环的精髓。

training.py：总教练

编排整个训练流程：读数据、分考卷、启动训练、保存模型并登记档案（pipeline/training.py:111）。

sequence.py：传送带

TubSequence / TfmIterator 把一条条记录变成"画面 x + 操作 y"的对子，源源不断地送上传送带（pipeline/sequence.py:134）。

augmentations.py：化妆师

给训练图片随机调亮度、加模糊，让 AI 见多识广，不挑天气（pipeline/augmentations.py:29-40）。

database.py：档案管理员

给每个模型编号起名（pilot_日期_序号），记录训练履历到 database.json（pipeline/database.py:37-50）。

动手入口：除了 donkey train 命令，车辆目录里还有一份现成的训练脚本模板 donkeycar/templates/train.py（由 donkey createcar 复制生成，见 management/base.py:107-131）。它会在启动时先配置好 GPU 显存上限和混合精度加速（templates/train.py:22-60），用法同样是 train.py --tubs data/ --model models/mypilot.h5。另外还有个贴心部件 TubWiper（tub_v2.py:144）：录数据时如果刚开撞了，按一下就能删掉最后 N 条"翻车录像"，免得 AI 把错误示范也学进去。

第 5 章　Web UI：浏览器里的驾驶舱

前面的章节告诉我们：车会自己跑、数据会录下来、模型能训练出来。但总不能每次都敲命令行吧？DonkeyDrift 的答案是 web_ui/——把整个自动驾驶工作流搬进浏览器。你打开一个网页，就能看车载摄像头的实时画面、拖方向盘开车、删掉录得不好的数据、点一下按钮开始训练。它就像一个网页版驾驶舱：仪表盘、方向盘、监控屏，全在浏览器标签页里。

这套系统采用经典的前后端分离架构：浏览器里的前端负责"长得好看、点得顺手"，电脑上的后端负责"真的干活"——读数据文件、跑训练、连车。两者之间用 HTTP 请求（像寄信：一问一答）和 WebSocket（像打电话：接通后随时互说）两种通道通信。

前端：六个页面各司其职。web_ui/frontend/src/App.tsx:102 里注册了全部路由：首页 / 是 Tub 管理页（浏览、删除录坏的驾驶数据），/drive 是驾驶页（DrivePage），/calibrate 是校准页（调舵机/油门中位与限幅），/trainer 是训练器页，/pilot 是模型竞技场（PilotArenaPage，让训练好的"AI 车手"离线跑预测、比成绩），/connector 是连车页。技术上它是 React 18 + TypeScript，用 Vite 打包（想象成把散装的乐高积木压成一块整板），Tailwind 负责样式，Zustand 像一块"共享白板"，各个页面把全局状态（比如当前打开的数据目录）写在上面，谁都能读。

后端：一个装配间 + 七组窗口。web_ui/backend/main.py:40 起，把 routers/ 目录下七个路由文件依次挂到 /api/config、/api/tub、/api/trainer、/api/drive、/api/arena、/api/connector、/api/provisioning——就像办事大厅开了七个窗口，前端想干什么就去对应窗口排队。比如驾驶页的实时操控走 routers/drive.py:498 的 WebSocket /api/drive/ws，摄像头画面则通过 WebRTC（一种浏览器原生的实时视频技术）在 /api/drive/webrtc/* 一组接口里协商建立。训练不归路由直接干，而是交给 trainer_engine.py 这个"工头"开后台任务，再用 SSE（服务器主动推消息的单向通道）把训练日志源源不断推回网页。连远程小车则由 connector_engine.py 和 remote_car_client.py 负责，通过 SSH/rsync 拉数据、推模型、远程启停驾驶。

为什么要分前后端？

分工像餐厅：前端是服务员，负责点菜界面好看、上菜及时；后端是后厨，真正掌勺。浏览器碰不到你电脑里的数据文件和串口，必须靠后端这个"本地人"代劳；而 Python 又不擅长画漂亮的交互界面，于是各干各的，中间用约定好的 API（窗口叫号规则）对话。

一条请求的旅程

你在训练器页点"开始训练"→ 前端 services/api.ts 发出 POST 到 /api/trainer/train/local → 后端 trainer_engine.py 启动训练进程 → 日志经 SSE 推回 → 网页上的进度条开始爬。全程你没碰过命令行，但背后跑的还是那个训练流水线。

⚠️ 安全提醒：仅限局域网！这个后端为了开发方便，把 CORS（浏览器的跨站访问门禁）设置成了"谁来都放行"（main.py:31，allow_origins=["*"]），而且没有任何登录认证——同一网络里任何人打开这个网址都能操控你的车。所以它只适合在家里或实验室的局域网用，千万别暴露到公网。

第 6 章：donkey CLI 与车辆模板 —— 一把瑞士军刀和一张预画好的乐高接线图

前面几章讲了零件（Part）、传送带（Vehicle 主循环）和共享白板（Memory）。可是一个新同学拿到项目后， 第一个问题往往是：「我该从哪条命令开始？」答案就是 donkey —— 它是整个项目的命令行入口， 像一把瑞士军刀：造车目录、校准舵机、开车、训练、画图，全都从这一个命令里弹出不同的「刀片」。 安装包时，setup.cfg 把 donkey 这个名字注册成 donkeycar/management/base.py:1182 的 execute_from_command_line() 函数； 你敲下 donkey createcar ...，它就在一张「命令字典」里查到对应的类，替你干活 （base.py:1186）。

瑞士军刀里到底有几把刀片？这不是文档抄来的，而是 donkeycar/management/base.py:1186-1203 的命令字典里真实注册的 16 个子命令：

造车与找车
  • createcar：用模板生成车辆目录（本章主角）
  • update：在已有车目录里更新到最新模板（base.py:152）
  • findcar：扫描局域网，找小车的 IP 地址（base.py:169）
  • calibrate：交互式校准舵机/电调的 PWM 值（base.py:189）
开车与训练
  • drive：一键拉起 Web UI 前后端 + 本车 manage.py drive（base.py:898）
  • train：用 Tub 数据训练模型，可选 tensorflow / pytorch（base.py:547）
  • models：查看模型数据库里的训练记录（base.py:594）
界面与数据工具
  • web / installweb：启动 Web UI / 装它的依赖（base.py:628、base.py:1031）
  • ui / tui：图形界面 / 终端界面（不带参数敲 donkey 默认进 TUI，base.py:1213）
  • tubplot / tubhist / makemovie / cnnactivations / createjs：数据画图、做视频、看神经网络「注意力」、配摇杆

createcar 干了什么？看 CreateCar.create_car()（base.py:84）就一目了然： 先建好 models、data、data_cache、logs 四个文件夹， 然后从 donkeycar/templates/ 目录里复制四样东西——模板代码（如 complete.py）改名成 manage.py，配套的 cfg_complete.py 改名成 config.py， 再加上 myconfig.py 和 train.py（base.py:104-131）。 默认模板叫 complete（base.py:93），但 templates/ 里还有 basic.py、arduino_drive.py（用 Arduino 当底盘驱动）、just_drive.py、 simulator.py 等多种「车型」可选，用 --template 指定。 还有个小细节：生成的 myconfig.py 里会自动附上 config.py 全部内容、但每行都注释掉 （base.py:138-147），像一份「出厂说明书」，想改哪项就取消注释哪行。

模板 = 一张预画好的乐高接线图。打开生成的 manage.py（即模板的副本）， 你会看到 drive() 函数先造一辆空车 V = dk.vehicle.Vehicle() （donkeycar/templates/complete.py:88），然后就是一长串 V.add(...)： 加相机、加手柄、加 AI 飞行员、加数据记录器……每次 V.add(部件, inputs=[...], outputs=[...]) 就像把一块乐高积木插到底板上，并用线把它的「输出插口」连到别人的「输入插口」。 比如 complete.py:150 把 user/steering 转接成 user/angle， complete.py:578 把一堆数据接进 TubWriter 录像机。 新手不用从零画这张图——模板作者已经把一辆能跑的车画好了。

那配置负责什么？决定接线图上每块积木的「型号」。模板里的接线经常藏在 if cfg.XXX 后面：比如 add_camera()（complete.py:908）读 cfg.CAMERA_TYPE 来决定插 PICAM、WEBCAM 还是 D435 深度相机这块「积木」； cfg_complete.py 里写着 CAMERA_TYPE = "PICAM"、DRIVE_LOOP_HZ = 20 这类出厂默认值。配置的读取机制在 donkeycar/config.py：Config.from_pyfile() 直接把你的 cfg 文件当 Python 代码执行（config.py:16-26），然后只收集全大写的变量 （config.py:28-31）。加载时先读 config.py，再找同目录的 myconfig.py 把同名变量覆盖掉（config.py:80-86）——就像学校发了一本标准实验手册， 你可以在自己的便利贴上写「我这台车的转向 PWM 通道是 0」，贴在手册上，运行时以便利贴为准， 而手册本身（模板文件）永远不被改脏。

记忆口诀：donkey 是瑞士军刀，createcar 是复印机 （把 templates/ 里的图纸复印成你的车辆目录），manage.py 是乐高接线图， config.py 是出厂手册，myconfig.py 是你的便利贴。 之后 donkey drive 让你当驾校教练开车收数据，donkey train 用这些数据教出 AI 学员 —— 整套流程不用写一行新代码。
